# MARCH 고민과 결정 기록

기존 기획서, 파일럿 구현 기록, 모델 비교와 Instagram 접근 검토를 바탕으로 정리했다. 실측값은 2026년 11월 4일의 실험 조건에 해당한다.

## 1. 공개 릴스 원문을 어떻게 확보할까?

가장 큰 미결정은 앱에 연결하지 않은 다른 사람의 **공개 Instagram 계정**에서 올린 릴스·게시글을 어느 정도 처리할 수 있는가다. 인증 배지, 계정 유형, 앱 권한, 콘텐츠 공개 범위는 따로 확인한다. 설명문·음성 전사·화면 글자·동작 중 사용자가 원하는 정보가 어디에 있는지 먼저 구분한다.

| 경로 | 쓰임 | 남은 확인 |
| --- | --- | --- |
| Meta 공식 DM + 소유·협력 계정 | 공유를 받고 권한 있는 설명문으로 저장부터 재검색까지 연결 | 공유 DM·URL DM·웹 URL에 실제로 들어오는 식별자와 본문, 일반 발신자와 앱 역할 사용자 차이 |
| Supadata | URL로 동영상의 화면·음성을 구조화하는 비교군. 설명문과 메타데이터는 별도 호출 | 한국어 정확도, 제3자 공개 링크 성공률, 비동기 처리 시간, 실패 포함 원가 |
| ScrapeCreators + 별도 모델 | 캡션·메타데이터·필요한 미디어를 수집하고 분석 모델은 따로 선택하는 비교군 | 반환 데이터와 권한, 수집·분석 이중 비용, 공급자 변경 대응 |
| 자체 획득 / 기기 측 입력 | 권한 있는 사용자 제공 파일, 브라우저 입력, OCR·STT 등으로 빈 부분 보완 | 추가 입력 부담, 보존·전송 범위, 접근 실패, 전력·배포·유지보수 비용 |

**결정** · P0의 기본 경로는 권한 있는 설명문이다. URL만 있으면 링크 보관으로 성공 처리하고 요약은 보류한다. 유료 획득 API는 비교군으로 둔다. YouTube Shorts·일반 동영상과 블로그는 저장을 지원하며, 본문·자막 획득은 출처마다 따로 검증한다. [Meta 공식 API](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api) · [Supadata Extract](https://docs.supadata.ai/get-extract)

**다음 실험** · 같은 콘텐츠를 공유 DM, 텍스트 DM, 웹 URL로 넣고 자체·협력·제3자 공개·접근 불가 콘텐츠를 나눠 기록한다. 확보한 설명문·자막·미디어, 실패 이유, 만료와 처리 범위를 적는다. 캡션만으로 충분한 레시피, 음성이 핵심인 후기, 화면에만 메뉴나 가격이 나오는 릴스를 구분한다.

## 2. 어떤 모델이 요약에 더 효율적인가?

Gemini 학생 Pro의 API 제공 범위와 OpenAI 구독에 연결된 크레딧을 활용할 수 있는지가 출발점이었다. 운영 판단은 계정별 크레딧 적용 여부, 실사용 품질, 성공 결과당 비용을 분리해 기록한다. 아래 비용은 당시 API usage에 실험 단가를 적용한 추정치다.

| 같은 한국어 합성 원문 30개 | GPT-6 Luna | Gemini 3.5 Flash-Lite |
| --- | ---: | ---: |
| 스키마·직접 인용·숫자·분량 검증 통과 | 30/30 | 27/30 |
| 총 추정 모델 비용 | $0.006095 | $0.031864 |
| 통과 결과당 추정 비용 | $0.000203 | $0.001180 |

**결정** · v0.2의 기본 텍스트 모델은 Luna로 유지한다. Gemini는 비교·대체 어댑터로 둔다. 외부 모델 없이 원문을 보여주는 발췌 모드는 명시적으로 선택하며, 기본 예시는 이 모드를 쓴다.

**남은 확인** · Gemini의 실패 3건은 직접 인용의 줄바꿈이나 연속 구절 불일치였다. Luna에서도 원문에 언급만 된 재료를 목록에 넣은 사례가 있었다. 합성 텍스트 결과이므로 실제 릴스, 긴 원문, 반복 측정, 사람 평가, 청구와 크레딧 차감은 별도 확인한다.

## 3. 영상 전체를 언제 분석할까?

설명문에 재료와 조리법이 모두 있으면 텍스트로 충분하다. 발화가 핵심이면 전사, 화면에만 가격·주소가 있으면 OCR·프레임, 조리 동작과 순서가 핵심이면 시간 순서가 있는 영상이 필요하다. 권한 있는 동일 영상으로 **텍스트만 / 직접 영상 모델 / STT·OCR·선택 프레임**을 비교하고 재료·계량·순서 오류와 유효 결과당 총원가를 측정한다.

## 4. 무엇을 자동으로 정리하고 어디까지 개인화할까?

저장 시 메모·태그·폴더를 강제하지 않는다. 요약·개체·내용 분류는 원문에 근거하고, 사용자 목적은 P0에서 `unknown`을 허용한다. 재료·수량·시간과 원문의 근거를 함께 보여준다. 개인 제목·태그·메모는 원문과 분리해 재분석 시에도 보존한다. 의미 검색이나 Chat은 한국어 기본 검색으로 필요한 항목을 찾아낼 수 있는지 측정한 뒤 비교한다.

## 5. 비용을 감당할 수 있고 반복해서 쓸까?

`유효 결과당 원가 = (획득 + 전처리 + 모델 + 저장·전송 + 실패·재시도 비용) / 활용 가능한 결과 수`로 비교한다. 본문 확보 실패도 파일럿의 전체 입력 수에 포함한다. 분석 전 예산을 예약하고 사용량으로 정산한다. 과금이 불명확하면 `unknown`으로 남기고 자동 유료 재시도와 고가 모델 전환을 피한다. 예산이 다 차도 링크 저장은 이어간다. 요금제와 포함량은 월간 사용량 분포, 재검색률, 비용, 지불 의향을 측정한 뒤 정한다.

## 6. 시스템과 배포를 어디부터 나눌까?

파일럿은 정적 웹, FastAPI, SQLite, 별도 Python Worker다. 데이터 소유권, 중복 접수, 작업 복구, 삭제 후 늦은 결과 차단을 우선한다. GitHub의 BE·FE·AI는 책임을 명확히 하는 경계다. 실행 코드를 나누는 시점에는 API와 분석 스키마의 버전을 맞추고 브라우저부터 DB까지 통합 경로를 재검증한다. Next.js·PostgreSQL, 배포, 앱·확장·결제는 파일럿 요구가 확인되는 순서로 검토한다.

## 7. P2에서 개인 보관함의 무엇을 함께 볼 수 있을까?

여행 일행이 후보를 한곳에 모을 수 있도록 별도의 공유 컬렉션을 검토한다. 개인 보관함에서는 카드별로 담을 컬렉션을 선택하고, 공유 전에 일행에게 보일 제목·요약·원본 링크를 확인한다. 개인 메모와 태그는 개인 보관함에 두고, 컬렉션에서는 공동 메모와 후보 상태를 따로 관리한다. [공유 흐름과 권한 초안](SHARING.md)
